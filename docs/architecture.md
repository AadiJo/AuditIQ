# Architecture

AuditIQ is one Node process with a SQLite database and a directory of uploaded files. The web app is a static single-page app that the same process serves.

```
apps/
  server/       Hono API, background runs, model runtimes, Jira sync
  web/          React app (Vite, TanStack Router and Query, Tailwind)
packages/
  shared/       zod schemas and types both sides use
e2e/            Playwright suite, fake Jira, test contract, replay fixtures
evals/          scoring against issues planted in the test contract
```

The server runs its TypeScript source directly on Node 24, so there's no server build. The web app's API types come from the server's route definitions through Hono's typed client (`apps/web/src/lib/api.ts`), so renaming a response field breaks the web build.

## A contract's path through the system

**Upload** (`documents/store.ts`). The file is stored under `DATA_DIR/files/<sha256>` and parsed once:

- DOCX: `documents/docx.ts` reads `word/document.xml` straight out of the ZIP with no dependencies.
- PDF: `documents/pdf.ts` rebuilds paragraphs from the text layer.

`documents/model.ts` then finds clause headings (`5.2.3`, `Article 5`, `Exhibit A`, `A.1`) and gives each clause an anchor id like `sec-5.2.3`. Everything before the first heading belongs to `preamble`. Identical bytes map to one document, because findings are keyed to the document's hash.

**Runs** (`runs/runner.ts`). Starting an agent inserts a queued run and returns. A small in-process queue executes runs two at a time. Each run:

1. builds the prompt: the contract as anchored clauses, plus the extraction output for the accounting review (`agents/prompts.ts`)
2. calls a runtime with the agent's JSON Schema
3. validates the output with the agent's zod schema
4. checks every quote and registers findings in one transaction

Every step is appended to `run_events`. The SSE route (`http/runs.ts`) replays stored events from the client's last sequence number, then streams live ones. That's why a reload, or a second person, sees the same progress. A restart marks in-flight runs failed and resumes queued ones.

**Runtimes** (`runtimes/`). Both runtimes implement one small interface: take a prompt and a schema, return JSON plus usage.

- `claude.ts` uses the Claude Agent SDK with `tools: []`, `settingSources: []`, an empty working directory, and the SDK's JSON Schema output.
- `codex/` talks JSON-RPC to `codex app-server`, which streams text deltas that the Codex SDK doesn't. Each run gets a private `CODEX_HOME` with tools off. Only the host's auth file and model provider carry over.
- Both prefer the CLI login on the machine and fall back to an API key.
- `replay.ts` serves recorded output for tests.

**Findings** (`findings/`). A citation counts only if its quote, after normalizing whitespace, quotes, dashes, and table separators, appears in the clause it names. A finding with any failing citation is held back from Jira, and the reason is stored.

A finding's identity is a hash of three things: the document's hash, the ASC 606 topic, and the primary clause, meaning the first quote, which the prompt asks agents to make the clause that raises the issue. Rewording, extra supporting quotes, reruns, and the same issue from both agents all land on one row, with one observation per run.

**Publishing** (`jira/publisher.ts`). Publishing queues one outbox row per finding per run. The dedupe key is unique, so replays add nothing. Each job looks for the finding's existing issue, first through the stored link and then by its `auditiq-fnd-<id>` label, before creating one. A later run's job adds a comment to the existing issue instead. Failures retry with backoff up to five times, and claims are leased so a crashed worker's jobs free up.

**Sync** (`jira/poller.ts`, `jira/service.ts`). A timer searches the project for `labels = "auditiq"` issues updated since a watermark, minus five minutes of overlap. It stores a snapshot of each issue, including comments, and records every issue update and comment once, keyed by Jira id. A six-hourly reconcile marks links whose issue vanished or lost its labels.

**Watcher** (`jira/watcher.ts`). A new comment that mentions `@AuditIQ` on a managed issue goes through fixed gates in order:

1. It's skipped if the service account wrote it or it carries an AuditIQ reply marker.
2. It's rejected on prompt-injection patterns.
3. It's rejected if the issue has no verified finding.

After that, the model proposes a reply, and the policy checks that it cites only the finding's verified clauses, is short, is confident enough, and fits the hourly budget. Shadow mode records the decision. Assist mode posts it with a marker, so a retry after a lost response is a no-op.

## Data

`apps/server/src/db/schema.ts` is the whole schema. Migrations in `db/migrations` are generated by drizzle-kit (`pnpm db:generate`) and applied at boot. Settings are typed JSON rows (`settings.ts`) with defaults, so new fields don't need migrations. Secrets inside them are sealed with AES-256-GCM (`crypto.ts`).

## Adding an agent

The planned third agent, a report writer, would take these steps:

1. Add its output schema and an entry to `agents` in `packages/shared/src/agents.ts`, with `dependsOn` naming the step it reads.
2. Add a prompt builder and version in `apps/server/src/agents/prompts.ts`, and a branch in the runner's prepare step.
3. Add its sections to `AnalysisView.tsx`.

The step tabs, run progress, findings, and publishing work from the registry without changes.
